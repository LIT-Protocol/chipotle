# Customer-path QA — 2026-09-16

## Scope and methodology

Tested the deployed https://keychain.litprotocol.com/ as a new user, following its published documentation and installing **@lit-protocol/keychain 2.0.2 from npm** (Node 22.22.0, npm 10.9.4). Repository implementation was inspected only after black-box findings were recorded, to implement fixes. No local source substitution, attestation bypass, real customer secrets, funded transactions, subscription purchase, or existing machine API credentials were used for production tests.

This is broad functional/DX coverage, **not a claim that every feature or security property was exhaustively verified**. Provider credentials, physical authenticators, Google login, billing and disaster recovery have explicit limits below. A test authenticator exercises real WebAuthn registration/signatures against production, not physical-device UX.

## Confirmed defects from the published/deployed product

1. **Default Node SDK omitted TLS-to-enclave binding.** The documented `new Keychain(identity.privateKey, config)` path successfully retrieved a dummy secret but reported five attestation checks; CLI `attest` reported those checks plus `tls-certificate-in-tee`. Documentation promised the latter for Node clients. No attacker-endpoint exploit was attempted.
2. **Published TypeScript declarations were not self-contained.** A minimal strict NodeNext consumer importing `Keychain` and `AgentConfig` failed TS2307 resolving `@lit-protocol/agent-keychain-library/schema`. Reproduced with TypeScript 5.9.3 and 7.0.2; `skipLibCheck` is not a fix.
3. **Identity validation ignored inconsistent metadata.** Explicit unsupported identity version and a public key that does not match the private key were accepted, sending users toward misleading permission failures. No authorization bypass demonstrated.
4. **Prototype-property secret names produced internal errors.** `constructor`, `toString`, and `__proto__` on an empty config bypassed ordinary unknown-secret handling. No disclosure demonstrated.
5. **MCP accepted object-valued JSON-RPC IDs.** `{"jsonrpc":"2.0","id":{},"method":"ping"}` was echoed as a valid response rather than rejected.
6. **Destroyed SDK clients attempted network execution.** `destroy(); get(...)` failed later with a misleading permission denial instead of rejecting locally.
7. **Adding a recovery passkey confused subsequent ordinary sign-in.** After registering an additional recovery passkey, the cached `keychain.passkey` selected the new credential. Ordinary sign-in opened a new empty vault belonging to that credential rather than the original vault. If the cached credential was unavailable while another approved one was present, the allow-list restricted selection to the missing credential. The original vault remained recoverable through explicit backup selection; this was not data loss.
8. **Broken public documentation targets.** `/README.md`, and the linked platform Derived Actions and Signed Storage pages returned HTTP 404. The platform attestation page and docs root returned 200. npm website 403 was an access barrier, not a dead link; registry retrieval worked.

Documentation gaps included export versus connected-service onboarding, Supabase's structured credential format, relative MCP paths, recovery prerequisites, distinct rotation operations, write retries, and statements overpromising credential confinement. Catalog contributor deprecation/immutability wording is outside this repository's fix scope.

## Production paths actually exercised

### Authentication and recovery

- Registered a resident, user-verified passkey via Chromium's virtual CTAP2 authenticator; production authorization, execution-key provisioning and empty-vault UI succeeded.
- Signed out and used the existing passkey to return to the same vault.
- Added an approved recovery passkey; active browser session was invalidated as advertised.
- Reproduced the cached-credential/wrong-vault problem above.
- Selected the original encrypted backup in **Recover an existing vault** and recovered the original vault.
- Downloaded a fresh backup after adding the recovery credential, removed the original credential from the test authenticator, signed out, loaded that backup and recovered the original vault using **only the recovery passkey**.
- Downloaded an encrypted backup and restored it when records already existed. This tests a no-op/conflict-safe round trip, not loss of the server database.

The browser process reset during the session, losing the first unpersisted virtual passkey. That is a test-infrastructure limitation, not a product bug; a second disposable vault used privately persisted test-authenticator material. Authenticator credential order was not treated as creation order after comparing IDs against backup authority metadata.

### Stored secrets and agent lifecycle

Only explicit dummy strings were stored: `QA_SMOKE` and `QA_LIFECYCLE`.

- Created secret, observed v1, zero initial agents, default 30-day permissions, and Free quota moving from 0/5 to 1/5.
- Approved an agent generated by the published CLI; downloaded its config.
- CLI, SDK and MCP successfully retrieved the expected dummy value with attestation enabled.
- A fresh unapproved identity was denied with actionable guidance.
- Disabled secret: CLI denied with owner-disabled message. Re-enabled: same config retrieved v1.
- Revoked agent: CLI denied with agent-not-approved message. Reapproved agent successfully.
- **Rotate & approve** produced v2 and migrated the existing grant. The **old downloaded agent config retrieved v2**; rotation did not consume another secret slot.
- Permission renewal input rejected 91 days (max 90); a one-day renewal changed the visible expiry.
- Owner export downloaded a JSON artifact; identity inspector showed action CID and ciphertext digest.
- Replaced execution key: old config failed with HTTP401/API key not recognized. Downloaded replacement config: same agent retrieved v2 successfully.
- Activity showed committed login, execution-key issuance, enrollment, creation and policy-management events. It is not a complete direct-Lit access audit.

### CLI and MCP handling

- `run` injected a secret into a child environment and propagated exit7 without the CLI printing the value.
- `--only`/`--env` selected and renamed the variable, excluding the original variable.
- `--file` delivered the dummy value in a mode0600 file and removed it after child exit.
- Existing files and symlinks were not overwritten.
- Missing executable and child SIGTERM both cleaned up temporary credential files; SIGTERM exit143 propagated.
- SDK repeated reads and MCP initialize/list/read worked.
- Offline cases covered malformed identity/config files, swapped artifacts, invalid JSON/action inputs, unknown secrets/commands, run mappings, release-mode mismatch, denial diagnostics, MCP parse errors, unknown methods, oversize frames and recovery.

### UX and service onboarding

- GitHub, OpenAI, Slack, Stripe and Supabase appeared in the service catalog.
- GitHub detail view described inputs, outputs, fixed host, timeout and response-size limits; malformed credential text was rejected before connection with a useful explanation.
- Mobile activity page at390×844 had no horizontal overflow. This is a spot check, not a comprehensive accessibility/device audit.
- Google uses a cross-origin iframe: its absence from top-level `document.body.innerText` is not evidence that the button is missing.

## Intermittent observations, not proven fixes

One agent retrieval returned a bare enclave denial despite the client-visible policy permitting access; subsequent reads and a repeat succeeded. One passkey login returned502 `lit_unavailable`; retry succeeded. These were recorded separately from deterministic defects. No root cause or general reliability guarantee is claimed.

## Blocked or untested acceptance criteria

- **Provider success paths:** no disposable Stripe/OpenAI/GitHub/Slack/Supabase credentials supplied. Successful `use` against those providers, provider-specific failure behavior and write deduplication remain unverified. No machine GitHub token was imported into Keychain.
- **Other auth:** Google consent/sign-in, wallet signing, physical/cross-device passkeys and OS prompts were not completed.
- **Billing:** paid checkout, cancellation, over-limit entitlements and high-volume fair-use enforcement were not exercised. No payment authorized.
- **Time/state:** actual passage beyond grant expiry, complete backend-data loss, replay/rollback attacks, cryptographic forgery, concurrency/load/fuzzing, disk forensics and multitenant host isolation were not tested.
- **Cleanup limits:** child SIGTERM was tested; SIGKILL cannot promise temporary-file cleanup and remains a documented limitation.

## Reproduction and privacy

Offline findings should be covered by committed regression tests. Public service documents audited were `/SKILL.md`, `/llms.txt`, `/SECURITY.md`, `/sdk/README.md`, the landing FAQ and published catalog documentation. Packed-package verification must install the tarball into an independent directory and compile a strict consumer, not resolve declarations accidentally through this monorepo's dependencies.

Do not attach agent identity files, virtual-passkey private material, scoped execution keys, downloaded agent configs or account backups to public reports. Production test values were dummy strings; owner/agent grants and billing credentials are still private artifacts. Changes in this PR are not proof that the public deployment or npm release has been updated.
