# Deploying a net‑new AccountConfig contract

This runbook covers standing up a **brand‑new `AccountConfig` diamond** and wiring
it to a running node. It is deliberately separate from the normal code deploy
(`.github/workflows/deploy-staging.yml`), because a fresh contract creates a
chicken‑and‑egg that the automated pipeline cannot resolve on its own.

## Why the payer must come from the KMS (the trust guarantee)

The api payer keys **must** be derived by the TEE's KMS — never generated by Lit,
an operator, or any human. This is not an operational convenience; it is the
core trust guarantee of API mode.

API mode acts **on behalf of users**: an api payer submits state‑mutating
transactions for accounts it does not own. The moment any party outside the
enclave can hold a key that acts on a user's behalf, that party can impersonate
the user, and the guarantee collapses. So the invariant is: **anyone (or
anything) that can act "on behalf of" a user must never be able to possess the
keys that do so.** The only thing permitted to hold them is the enclave itself,
where access is gated by the TEE and by the attested code running inside it.

That is exactly why the payer is a stateless KMS derivation and why this runbook
never asks you to create or import a payer key. You bring up the TEE, and the
enclave — not you — derives the payer and signs with it. The one human action is
telling the on‑chain contract which enclave‑derived address to trust
(`setAdminApiPayerAccount`), which grants authority *to the TEE* without ever
exposing the key to an operator.

## The problem this solves

A freshly deployed `AccountConfig` diamond boots with an **empty** api‑payer set
and a **zero** admin payer:

- `contracts/AccountConfig.sol` — constructor sets `requestedApiPayerCount = 3`
  (just a default) but leaves `adminApiPayerAccount = 0x0` and `api_payers` empty.

With no payer registered on‑chain, the node cannot service `POST /new_account`
(`src/accounts/mod.rs` → `"No api_payers configured; cannot simulate account_exists"`),
so every k6 correctness/smoke run fails against the new contract. And the payer
addresses are only knowable from a **running** node (they are dstack derivations,
see below) — hence the egg‑before‑chicken.

The automated `deploy-staging.yml` pipeline makes this worse, not better: it runs
`deploy → wait-for-api → k6-smoke/correctness → cutover`, and on a k6 failure the
`rollback-on-failure` job **stops the freshly‑deployed cold CVM**. So if you push a
contract swap through the normal pipeline, the node you need to query gets torn
down the moment k6 goes red — before you ever get a chance to configure the payer.

**The fix: bring the Phala TEE up manually and keep it live** long enough to read
its admin payer, set that payer on the new contract as the owner, let the node
self‑register the payer set, and re‑seed the k6 account pool. Only then do you let
the normal pipeline gate and cut over.

## Key fact: the payer is derived, not stored, and is contract‑independent

The admin payer and api payers are **stateless dstack key derivations**. Inputs are
a fixed path string + purpose only (see `src/dstack/v1/mod.rs`):

```rust
get_admin_api_payer_key()  // path "v1/admin_api_payer", purpose "lit_payer"
get_lit_payer_key(n)       // path "v1/payer_{n}",       purpose "lit_payer"
```

The contract address is **not** an input to the derivation — `contract_address`
from `NodeConfig.toml` only tells the node *where to register/query* payers
(`src/accounts/signable_contract.rs`). Consequences:

- Swapping to a new contract on the **same dstack app** yields the **same** payer
  addresses. You can read them from any already‑running node with that `app_id`.
- A **new Phala CVM with a new `app_id` / AppAuth KMS** has a different master key,
  therefore **different** payer addresses. In that case you *must* query the new
  node itself — which is why the manual, stay‑alive TEE step below is required.

> Shortcut when the `app_id` is unchanged: you can read `/get_admin_api_payer` from
> the *currently‑live* node before you deploy anything, pre‑seed the new contract
> (steps 4–5), and skip the manual TEE. The full manual procedure below is the
> general case that also works for a brand‑new app_id.

## Prerequisites

- Foundry (`cast`) and `jq` on PATH.
- Phala CLI: `npm install -g phala@1.1.19` (match the pinned version in
  `deploy-staging.yml`).
- The **deployer secret** for the target network (`DEPLOYER_SECRET` for `make deploy_*`; `BASE_DEPLOYER_SECRET` only for Base mainnet `update_base` / `propose_update_base`).
- Authority to send the bootstrap tx from the **diamond owner** — on Base this is
  the owner/Safe set at deploy time. On a fresh diamond, `adminApiPayerAccount`
  is `0x0`, so `setApiPayers` is **owner‑only** until the admin payer exists
  (`AccountConfigFacets/SecurityLib.sol::revertIfNotOwnerOrAdminApiPayer`).
- Base ETH to fund the admin payer (it in turn funds the child payer signers).
- `PHALA_CLOUD_API_KEY` and `PHALA_DSTACKAPP_PRIVATE_KEY` for the target CVM/app.

## Step 1 — Deploy the new AccountConfig diamond

From `lit-api-server/blockchain/lit_node_express/`:

```bash
# Base mainnet
make deploy_base       # DEPLOYER_SECRET must be set
# or Base Sepolia
make deploy_sepolia
```

These build and run `contract_deployer --action=deploy --network=<net>
--abifolder=artifacts/contracts --secret=<key>`. **Record the deployed diamond
address.** Verify it on Basescan per `lit_node_express/README.md`.

If you changed any Solidity, regenerate the Rust bindings first (Makefile
`compile` target / the ABI pipeline in `lit_node_express/AGENTS.md`) and commit
`src/accounts/contracts/AccountConfig.json` + `account_config_contract.rs`.

## Step 2 — Point the node config at the new contract

Edit the `contract_address` under `[chain]` in the `NodeConfig.*.toml` for the
target environment (this value is baked into the image at build time — this is
exactly what PR #671 did):

- `NodeConfig.next.toml`  → chipotle‑next / staging (Base)
- `NodeConfig.main.toml`  → Base
- `NodeConfig.prod.toml`  → production (Base mainnet)

```toml
[chain]
name = "base"
contract_address = "0x<new-diamond-address>"
```

Commit and build the image (or build locally for a manual deploy in Step 3).

## Step 3 — Bring up the Phala TEE **manually** and keep it live

Do **not** push this through `deploy-staging.yml` yet. That pipeline's
`rollback-on-failure` job stops the cold CVM as soon as k6 fails — and k6 *will*
fail until payers are registered. Instead, deploy the node by hand so it stays up:

```bash
# Render the digest-pinned compose file the same way the pipeline does
# (see deploy-staging.yml "Prepare docker-compose for deployment"), producing
# docker-compose.deploy.yml, then:

phala deploy \
  -c docker-compose.deploy.yml \
  --cvm-id <target-cvm-name-or-id> \
  --private-key "$PHALA_DSTACKAPP_PRIVATE_KEY" \
  -e "BASE_CHAIN_RPC=$BASE_CHAIN_RPC" \
  -e "STRIPE_SECRET_KEY=$STRIPE_SECRET_KEY" \
  -e "STRIPE_PUBLISHABLE_KEY=$STRIPE_PUBLISHABLE_KEY" \
  -e "GCP_SERVICE_ACCOUNT_JSON=$GCP_SERVICE_ACCOUNT_JSON" \
  -e "GCP_PROJECT_ID=$GCP_PROJECT_ID" \
  # ... remaining certbot/otel env vars as in deploy-staging.yml
```

Notes:
- For a **new** CVM, provision it (Phala Cloud dashboard or `phala cvms create`)
  and allowlist **both** ping‑pong devices on the app's AppAuth contract
  (`phala cvms device-allowlist`) so the shared `app_id` derives keys on either
  node — see the header of `deploy-staging.yml`.
- The node boots fine against a fresh contract with no payers. Payer absence
  breaks *mutations*, not boot; the read endpoints you need in Step 4 are up
  (`src/main.rs` comment: "nothing will work until an admin sets the default api
  payer").
- Because you invoked `phala deploy` directly (not via a `main` push), nothing
  will stop this CVM out from under you. It stays live for as long as you need to
  finish Steps 4–7.

Confirm it is serving on its own default Phala URL before continuing:

```bash
curl -fsS https://<cold-cvm-phala-url>/version
```

## Step 4 — Read the admin payer from the live node

```bash
curl -fsS https://<cold-cvm-phala-url>/get_admin_api_payer
# → the admin api payer address this node derives from its dstack app key
```

(You can also read the full expected payer set with `/get_api_payers`.)

## Step 5 — As the diamond owner, set the admin payer on the new contract

Send from the diamond **owner** (Safe or owner EOA). Using `cast` against Base:

```bash
cast send "$NEW_CONTRACT" 'setAdminApiPayerAccount(address)' "$ADMIN_API_PAYER" \
  --rpc-url "$BASE_CHAIN_RPC" --private-key "$OWNER_KEY"

For a Safe‑owned diamond, route this through the Safe UI / a proposal instead of a
raw key. The monitor dApp also exposes this flow
(`lit-static/dapps/monitor/app.js` → `setAdminApiPayerAccount`).

Then fund the admin payer with Base ETH so it can pay gas for `setApiPayers` and
top up the child payer signers:

```bash
cast send "$ADMIN_API_PAYER" --value <amount>ether \
  --rpc-url "$BASE_RPC" --private-key "$OWNER_KEY"
```

> Reference implementation of the full local wiring (owner → `setAdminApiPayerAccount`
> → `setApiPayers` → fund) is `local_test.sh` Step 3b (Anvil). In production you do
> the owner tx by hand and let the node do `setApiPayers` itself (Step 6).

## Step 6 — Let the node self‑register the payer set

Once the node's admin payer is the on‑chain admin, the signer pool reconciler
grows the pool to `requestedApiPayerCount` and calls `setApiPayers([...])` signed
by the admin payer, then rebalances gas to the child signers
(`src/accounts/signer_pool.rs` → `set_api_payers`, `rebalance_entries`). You do
not need to know the child payer addresses in advance.

Verify the set filled and is funded:

```bash
curl -fsS https://<cold-cvm-phala-url>/get_api_payers
# and on-chain:
cast call "$NEW_CONTRACT" 'apiPayerCount()(uint256)' --rpc-url "$BASE_RPC"
```

Optional: adjust the desired count with `setRequestedApiPayerCount(uint256)`
(owner/admin‑payer gated) before or after this step.

Smoke‑test account creation now works:

```bash
curl -fsS -X POST https://<cold-cvm-phala-url>/new_account \
  -H 'content-type: application/json' \
  -d '{"account_name":"bootstrap-check","account_description":"deploy.md"}'
```

## Step 7 — Re‑seed the k6 account pool against the new contract

The committed pools (`k6/data/accounts.next.json`, `k6/data/accounts.dev.json`) hold API

```bash
cd k6
BASE_URL=https://<cold-cvm-phala-url> \
K6_ACCOUNTS_FILE=./data/accounts.next.json \
  k6 run accounts.seed.spec.ts
```

Commit the regenerated `accounts.*.json`, or pass it to CI via the `accounts_json`
secret consumed by `k6-smoke.yml` / `k6-correctness.yml`.

## Step 8 — Hand back to the normal pipeline

With payers registered and the k6 pool re‑seeded, the standard flow is safe:

- Let `deploy-staging.yml` run `k6-smoke` → `k6-correctness` → `k6-loadtest`
  against the cold CVM's own URL, then `confirm-cutover` flips DNS.
- The k6 gate now passes on the first run, so `rollback-on-failure` won't fire.

## Checklist

- [ ] New diamond deployed (`make deploy_base`), address recorded + verified.
- [ ] `NodeConfig.<env>.toml` `contract_address` updated + committed.
- [ ] TEE brought up **manually** (`phala deploy`), confirmed live on its own URL.
- [ ] Admin payer read from `/get_admin_api_payer`.
- [ ] `setAdminApiPayerAccount` sent from the diamond owner; admin payer funded
      with Base ETH.
- [ ] `/get_api_payers` non‑empty and funded; `/new_account` returns 200.
- [ ] k6 pool re‑seeded (`accounts.seed.spec.ts`) and committed / wired via
      `accounts_json`.
- [ ] Normal pipeline green; cutover completed.
