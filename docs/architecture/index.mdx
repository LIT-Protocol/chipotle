Lit Chipotle is built on three composable layers that each handle a distinct concern. Understanding the separation makes it easier to reason about security, auditability, and where your own code fits in.

The throughline: **your keys' authority lives on-chain, and an attested TEE enforces it by reading the chain.** We call this [Chain Secured](/architecture/chain-secured) — on-chain authority, signing at the speed of an API call.

## The Three Layers

**TEE Enclave (Phala / dstack)**
The enclave holds the root key and performs all sensitive operations: key derivation, authorization checking, and sandboxed Lit Action execution. Nothing that touches key material ever leaves the enclave. The TEE also acts as a convenience relay for API-mode accounts — it can sign and submit on-chain management transactions on your behalf after verifying your API key scopes.

**On-Chain Permissions (Base)**
All authorization state lives on-chain in a set of smart contracts: an Account contract that registers the owner address, an API Key Registry mapping key hashes to scopes, a PKP Registry of wallet derivation path IDs, and Groups that bind PKPs to permitted action CIDs. The TEE reads these contracts to decide whether to execute a request. You can update them through the TEE relay (API mode) or by submitting transactions directly from the owner's EOA or multisig (the only way in ChainSecured mode).

**Lit Actions (IPFS)**
Lit Actions are immutable JavaScript programs referenced by their IPFS content ID (CID), which is a hash of the code. They are not owned by anyone — they are public, reusable, and content-addressed, similar to npm packages. You can pin an action to IPFS to share it, but the TEE does not fetch actions from IPFS. You send the code with the request (or the CID of code the server has already cached), the TEE hashes it to get the CID, and then it runs the code inside a sandboxed JS environment that has access to the derived key material.

## Follow one request

Here is one request from start to finish. Your app holds a usage key with execute permission in group 7. Group 7 lists the action `QmABC` and the PKP `pkp_001`. The app sends the action's code, with `{"pkpId": "pkp_001"}` as its `js_params`.

<RequestPath />

1. The server hashes the code. The hash is `QmABC`, so this is the action that group 7 lists.
2. It checks the account's rules on Base. The key may execute in group 7, and group 7 lists `QmABC`, so the code may run.
3. The TEE runs `main(js_params)`.
4. The action calls `Lit.Actions.getPrivateKey({ pkpId: "pkp_001" })`. Group 7 lists both `QmABC` and `pkp_001`, and the key can use group 7, so the TEE derives the key and the action signs.
5. The response carries whatever `main` returned, such as the signature.

If a check fails, nothing is signed. A key without permission stops at step 2. Code that changed by one character has a different CID, so it also stops at step 2. A PKP that isn't in the group stops at step 4. The [Authentication Model](/architecture/authModel#execution-flow-inside-the-tee) walks through the same flow from the contract's side.

## API mode vs ChainSecured mode

Both modes run the same code, and which one you use is a configuration choice. They differ in who owns the account. In **API mode**, a Lit-managed credential owns the account and relays your admin writes — the fastest way to start. In **ChainSecured mode**, a wallet you control (an EOA or Safe) owns the account on-chain and signs every change itself — fully self-custodied, with an on-chain audit trail. Both run the same contracts and the same Lit Actions; only account ownership and how writes are signed differ.

See [API Mode vs ChainSecured Mode](/management/account_modes) for the side-by-side and the migration path.
