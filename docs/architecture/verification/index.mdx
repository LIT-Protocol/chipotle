The Lit Chipotle API server runs inside an AMD SEV-SNP [Trusted Execution Environment](https://www.amd.com/en/developer/sev.html) on [Phala Cloud](https://phala.com/), with its keys gated by smart contracts on Base. This section explains how that works and how to verify it yourself.

There are two layers of checks. The hardware shows which Lit release is running, and the chain says which releases can hold keys. Pick the page that matches your question:

- **What does attestation prove, and why can I trust it?** Start with [What Is Attestation?](/architecture/verification/attestation).
- **Is the live API running approved code right now?** Run the checks in [Verify in 30 Seconds](/architecture/verification/quick-verify).
- **Who approves a new release, and how are keys released to it?** Read [On-Chain KMS](/architecture/verification/onchain-kms) and [Upgrade Governance](/architecture/verification/upgrade-governance).
- **Why does each check matter?** The [Chain of Trust Reference](/architecture/verification/chain-of-trust) explains each step.
- **How do I enforce this in my own client?** Use the SDK, as [Production verification](#production-verification) below describes. The [Full Verification Guide](/architecture/verification/full-verification) repeats each check by hand.
- **I found a problem.** See the [Bug Bounty](/architecture/verification/bug-bounty).

A Trust Center report or a matching hash tells you what the server is running. It does not protect a later connection by itself. Your client has to check the evidence and pin the TLS key on the connection that carries your data. The SDK does both.

## Production verification

Use [`@lit-protocol/core-sdk`](https://www.npmjs.com/package/@lit-protocol/core-sdk). A client created for the production API verifies the server before its first request and refuses to send if verification fails:

```javascript
import { createClient, LIT_API_URL } from '@lit-protocol/core-sdk';

const client = createClient(LIT_API_URL); // https://api2.chipotle.litprotocol.com
```

It checks the AMD signature on the attestation report, that the report is fresh, the OS image and the app the VM booted, and that Lit's multisig approved both on Base. In Node.js it also checks that the TLS key of the connection belongs to the attested VM and pins every API connection to that key. It verifies again in the background every ten minutes. Create one client per process and reuse it.

If you call the HTTP API without the SDK, nothing verifies the server for you. What you need then depends on where and how your client connects, including any proxy or gateway of your own that terminates TLS. Verify the attestation against the policy you accept, and bind the verified identity to the connection that carries application traffic before you send secrets. `verifyAttestation` and `createPinnedFetch` from `@lit-protocol/core-sdk/attestation` do this for any Node.js HTTP client; see the [Full Verification Guide](/architecture/verification/full-verification).

<Note>
The previous hostname, `api.chipotle.litprotocol.com`, runs on Intel TDX and is retired on December 31, 2026. The SDK does not verify it. See [Migrate to the new API hostname](/management/migrate-to-api2).
</Note>

## Zero-Trust TLS

**What is Zero-Trust TLS?** In traditional web hosting, you trust the server operator not to inspect or tamper with your traffic. Zero-Trust TLS (ZT-TLS) eliminates this trust assumption entirely. The TLS private key is generated **inside** the Trusted Execution Environment (TEE) and **never leaves it** — not even the cloud provider, OS administrator, or Lit Protocol team can extract it.

**How it works for Lit Chipotle:**

1. The [dstack-ingress](https://github.com/Dstack-TEE/dstack-examples/tree/main/custom-domain/dstack-ingress) container, running inside the CVM, generates a private key and requests a TLS certificate from Let's Encrypt via DNS-01 challenge (Route 53). The private key never leaves the TEE.
2. The certificate and ACME account are recorded as evidence files. Their SHA-256 checksums are hashed into a single digest that is embedded in the report data of an AMD SEV-SNP attestation report.
3. Because the report is signed by the processor and bound to this digest, anyone can cryptographically prove the certificate was obtained inside a VM of this app.

**What you must verify:** A valid public-CA certificate and successful TLS handshake do not by themselves prove TEE termination. Verify the evidence report and the approved workload, verify the certificate's checksum binding, and enforce that key on the connection used for application traffic. The SDK does all three in Node.js.

**Contrast with traditional TLS:** Traditional TLS proves identity (the server holds the private key for this domain) but says nothing about *where* the key lives or *what code* uses it. ZT-TLS closes that gap: the key can only exist inside attested TEE hardware.

<Note>
Zero-Trust TLS means the encryption endpoint is the trust boundary. Once you verify the certificate was issued to the TEE, the HTTPS connection itself becomes your proof of confidentiality.
</Note>

For the full design, see [Phala: TEE-Controlled Domain Certificates](https://docs.phala.com/dstack/design-documents/tee-controlled-domain-certificates).

## Inspect the TLS Certificate

The command below only inspects the certificate. It does not verify an attestation report or prove TEE termination.

```bash
# Inspect the TLS certificate
openssl s_client -connect api2.chipotle.litprotocol.com:443 \
  -servername api2.chipotle.litprotocol.com </dev/null 2>/dev/null \
  | openssl x509 -noout -fingerprint -sha256 -dates -subject
```

- The certificate is issued by **Let's Encrypt** (a public CA) to the exact domain.
- Public-CA validity alone does not prove that the private key lives in a TEE. See Step 3 of the [Full Verification Guide](/architecture/verification/full-verification).

## Key Pinning

The SDK pins the TLS public key, not the certificate, because a certificate is renewed while its VM keeps running.

1. Verification returns `tlsKeySha256`, the SHA-256 of the attested TLS public key.
2. Every API connection the client opens must present that key, or the request fails before anything is sent.
3. **Releases.** Each release starts a new VM with a new key, and for a short time both VMs serve the hostname. The client verifies whichever VM a connection reaches and pins the keys of both, so requests carry on through the changeover. A key stays pinned for at most an hour after it was verified.

If you pin in your own HTTP client, re-verify when a connection presents a key you have not seen, and do not pin a key for longer than you would trust a verification.
