Every other page in this section tells you *how* to verify Lit Chipotle. This page
explains *what you are actually verifying* and *why it is trustworthy* — in plain
language, before any commands. If you have never worked with a Trusted Execution
Environment (TEE) before, start here.

## The problem attestation solves

When you send data to an ordinary cloud server, you are trusting a lot of people you
will never meet: the application operator (Lit), the cloud provider (Phala),
the OS administrators, anyone with physical access to the machine. Any of them
*could*, in principle, read your data, swap the code for a malicious version, or
copy out a private key. You have no way to tell. "Trust us" is the only guarantee.

**Remote attestation removes that trust.** It lets a remote machine produce
hardware-signed, mathematical proof of *exactly what code it is running*. You can
check the proof yourself, and no operator (including Lit) can forge it. You no longer
have to trust the operator. You still trust the processor maker's hardware (AMD's) and the math that checks
its signature.

Attestation tells you which code is running. It doesn't tell you that the code is free
of bugs, which is one reason the Lit Chipotle source is public.

This is the idea behind the broader [Proof of Cloud](https://proofofcloud.org/)
movement: cloud services that prove what they run rather than asking you to take
their word for it.

## What a TEE is

A **Trusted Execution Environment** is a hardware-isolated region of a CPU. Lit
Chipotle runs inside **AMD SEV-SNP** (Secure Encrypted Virtualization with Secure Nested
Paging), a TEE built into AMD EPYC server chips. Inside the TEE:

- Memory is **encrypted by the CPU**. Even someone with root on the host, physical
  access to the RAM, or a hypervisor cannot read the plaintext.
- The launch is **measured**. Before the VM starts, the processor hashes its initial
  state (firmware, kernel, boot parameters) into a value the VM cannot change.
- Secrets generated inside (like the TLS private key) **never leave**. There is no
  API to extract them, by design.

Lit Chipotle runs as a confidential virtual machine, or **CVM**, inside SEV-SNP. These
pages use "CVM" for that machine and "enclave" as another word for the TEE.

A TEE is not magic — it rests on the assumption that AMD's hardware root of trust
is sound, and TEEs have known classes of side-channel research. But it replaces *many
fully-trusted humans* with *one well-studied hardware assumption you can reason
about*.

## What an attestation report is

On request, the processor produces an **attestation report**: a small binary document,
**signed by a key that only that AMD chip holds**, that describes the VM it is running.
Think of it as a notarized receipt the silicon hands you, saying "here is exactly what
I am running." (Intel calls the same thing a quote.)

Three fields carry most of the weight:

| Field | What it records |
|---|---|
| **Launch measurement** | One hash over the virtual firmware, kernel, initial filesystem and boot parameters, i.e. the **operating system** |
| **`HOST_DATA`** | A value fixed when the VM launches. It is the hash of a document that names the **application**: Lit's app id, the hash of the docker-compose configuration (the *compose hash*, computed over `app-compose.json`), and which KMS issues its keys |
| **Report data** | 64 bytes chosen by whoever asked for the report. A verifier puts a random number here so the report is provably fresh |

Two numbers come out of these:

- The **OS image hash** identifies which operating system image booted. The launch
  measurement can be recomputed from that image's published parts.
- The **compose hash** proves which application code booted — it is the
  SHA-256 of `app-compose.json`, which holds the exact, image-digest-pinned
  docker-compose that defines Lit Chipotle, plus its metadata. The explainer videos
  call it the release hash.

If even one byte of the OS or the application changes, these numbers change, and the
report no longer matches what is expected. For example, if a payment program that sends
1,000 were changed to send 1,001, its hash would come out completely different.

## How a stranger turns a report into trust

Receiving a report is not enough — anyone can hand you a document. The value comes
from four independent checks, each of which you can run yourself:

1. **Is the report real?** Verify the chip's signature on the report, and the chip's
   certificate against AMD's published root keys. This proves the report came from
   genuine SEV-SNP hardware (not a simulator, not debug mode). Check too that it
   answers the random number you just sent, so it is not a recording.

2. **Is the OS one I trust?** Check the launch measurement against a known-good dstack OS
   release — and confirm that release is whitelisted on-chain (see below).

3. **Is the code one I trust?** Recompute the compose hash from the public source and
   confirm it matches the report — and that it is whitelisted on-chain.

4. **Am I really talking to that TEE?** The TLS certificate for
   `api2.chipotle.litprotocol.com` was generated *inside* the TEE and bound into a
   signed report. Once you have checked that binding and pinned the certificate, a successful
   HTTPS handshake proves your connection terminates in the attested enclave — no
   proxy in the middle. A handshake on its own, before those checks, does not prove
   this. (See [Zero-Trust TLS](/architecture/verification/index#zero-trust-tls).)

The crucial move is in steps 2 and 3: "a version I trust" is not decided by Lit. It
is decided by a **whitelist held in smart contracts on Base**, governed by a Safe
multisig. Lit cannot ship code to the production enclave without first getting that
code's compose hash approved on-chain, in public, by multiple signers. That is what
the [On-Chain KMS](/architecture/verification/onchain-kms) page covers, and the
approval process itself is documented in
[Upgrade Governance](/architecture/verification/upgrade-governance).

## Why this is stronger than "trust the operator"

Put the pieces together and the trust model inverts:

- The **cloud provider** cannot read your data — memory is CPU-encrypted.
- **Lit** cannot silently change the code — a new version cannot get keys until its
  compose hash is whitelisted on Base by a multisig, visible to everyone.
- **No single Lit employee** can change that whitelist — it takes a multisig quorum.
- **You** do not have to trust any of the above — you re-derive every measurement and
  read the on-chain whitelist yourself.

That is the whole point of attestation: you check the evidence yourself instead of
taking anyone's word for it.

## The SDK runs these checks for you

[`@lit-protocol/core-sdk`](https://www.npmjs.com/package/@lit-protocol/core-sdk) runs
all four checks with no configuration. A client created for the production API
verifies the server before its first request, and if verification fails the request
rejects with an `AttestationError` and nothing is sent:

```javascript
import { createClient, LIT_API_URL } from '@lit-protocol/core-sdk';

const client = createClient(LIT_API_URL);
const proof = await client.verifyAttestation();
// { platform: 'sev-snp', appId, composeHash, osImageHash, tcbStatus, tlsBinding, ... }
```

Three things make the check hold for the requests that follow, not only for the moment
it ran:

- **Freshness.** The SDK sends a random nonce to `GET /attestation/v3?nonce=…` and
  requires the signed report to commit to it, so a response cannot be replayed.
- **The connection is pinned.** In Node.js the SDK checks that the TLS key of its
  connection belongs to the attested VM, then pins every API connection to that key.
  A request can only reach a VM that was verified.
- **It re-verifies.** After ten minutes the client verifies again in the background,
  and a client idle for over an hour verifies before its next request.

Only the first request waits for verification, which takes one to two seconds.

Failures throw an `AttestationError` with a stable `code` (for example
`untrusted_hardware`, `stale_evidence`, `measurement_mismatch`, `not_governed`,
`tls_binding_failed`).

Browsers cannot read or pin TLS certificates: there the check proves that genuine
Lit evidence was served at the origin, and the requests that follow rely on the
browser's own TLS validation. Verify from a server when the channel matters.

The check trusts AMD's root key and the Base blockchain. It reads Base through public
RPC endpoints by default; pass your own with `attestation: { rpcUrls: [...] }` for
stronger guarantees.

## If you do not use the SDK

Calling the HTTP API directly works, and nothing verifies the server for you. To get
the same guarantee, verify the attestation and bind the verified identity to the
connection that carries your requests, including through any proxy or gateway of your
own that terminates TLS. The [Full Verification Guide](/architecture/verification/full-verification)
shows each check and how to pin a connection to the verified key.
