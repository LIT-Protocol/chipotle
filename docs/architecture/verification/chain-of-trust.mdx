The sections below explain what each verification step is actually checking and why it matters. For the step-by-step commands, see the [Full Verification Guide](/architecture/verification/full-verification). The Core SDK's `verifyAttestation` performs every check marked **SDK**.

## Platform Layer

The Lit API runs in an AMD SEV-SNP confidential VM. The processor signs an attestation report containing these fields:

| Field | What it carries |
|----------|-----------------|
| **Launch measurement** | One hash over the VM's initial state: virtual firmware, kernel, initrd, kernel command line and CPU count. |
| **`HOST_DATA`** | A hash supplied at launch and fixed for the life of the VM. dstack sets it to the hash of the app identity document. |
| **Report data** | 64 bytes chosen by the software that requested the report. Used to bind a nonce or a certificate manifest. |
| **Guest policy** | Whether debugging and migration are allowed. |
| **TCB versions** | The firmware and microcode versions of the platform. |

| Check | What it proves |
|-------|----------------|
| **Report signature** (SDK) | The report is signed by the chip's key (VCEK). That key's certificate chains through AMD's intermediate (ASK) to an AMD root key (ARK). A valid chain proves the report came from a genuine AMD processor running SEV-SNP, not from a simulator. |
| **Freshness** (SDK) | The verifier sends a random nonce and requires the report data to commit to it. An old report cannot be replayed. |
| **Guest policy** (SDK) | A VM with debugging enabled can be read by its host. The verifier refuses one. |
| **OS image** (SDK) | The verifier recomputes the launch measurement from the firmware, kernel, initrd and command line the VM declares and compares it with the signed value. The command line carries the hash of the root filesystem, so the measurement identifies one dstack OS image. The **DstackKms** contract allowlists OS images via `allowedOsImages(bytes32)`. |
| **KMS attestation** | The KMS itself runs in a TEE with its own attestation. [Phala's Trust Center](https://github.com/Phala-Network/trust-center) verifies this independently. The DstackKms contract allowlists KMS instances via `kmsAllowedAggregatedMrs(bytes32)`. |

## Application Layer

| Check | What it proves |
|-------|----------------|
| **App identity** (SDK) | The signed `HOST_DATA` equals the hash of the app identity document, which names the `app_id`, the compose hash and the key provider. A VM launched for a different app or a different compose document has a different `HOST_DATA`. |
| **compose-hash** | The compose hash is the SHA-256 of `app-compose.json`, which includes `docker-compose.yaml` plus metadata. Recomputing it from `/info` and comparing it to the attested value proves the CVM runs the configuration it publishes. |
| **Docker image digests** | All images (lit-actions, lit-api-server, otel-collector, dstack-ingress) use `@sha256:` digest pinning. Mutable tags like `:latest` would allow silent image substitution. |
| **Image provenance (Sigstore)** | Each image is signed with Sigstore cosign (keyless, GitHub OIDC). Verification proves the image was built by GitHub Actions from the `LIT-Protocol/chipotle` repository and recorded in the public Rekor transparency log. |

## Network Layer

| Check | What it proves |
|-------|----------------|
| **Evidence files** | dstack-ingress serves `/evidences/` with `cert-<domain>.pem`, `acme-account.json`, `sha256sum.txt` and `attestation.json`. |
| **Evidence binding** (SDK) | The report data of the attestation in `attestation.json` equals `SHA-256(sha256sum.txt)`, and the report is verified like the main one and must come from the same app. This proves the certificate in the manifest was obtained inside a VM of the governed app. |
| **TLS key match** (SDK, Node.js) | The public key of the certificate presented on the connection equals the public key of the attested certificate. This proves the connection ends in that app. |
| **Key pinning** (SDK, Node.js) | A client pins later connections to the verified key, so a connection that presents any other key fails. Without pinning, a check made on one connection does not cover the next. |

## Governance Layer

| Check | What it proves |
|-------|----------------|
| **DstackApp contract** ([`0x3F91…05FfC`](https://basescan.org/address/0x3F91Deaf16FF7C823eE65081d6bAFA1cEea05FfC)) | The compose-hash must be allowlisted via `allowedComposeHashes(bytes32)` before the KMS will release keys to the CVM. Address matches the `app_id` returned by `GET /info`. |
| **Phala KMS contract** ([`0x2f83…Ba9C`](https://basescan.org/address/0x2f83172A49584C017F2B256F0FB2Dca14126Ba9C)) | Whitelists allowed OS images (`allowedOsImages`) and KMS instances (`kmsAllowedAggregatedMrs`). Only allowlisted versions receive keys. | **AccountConfig contract** | Governs Lit Chipotle's permission model on Base — account ownership, API key scopes, PKP registries, and action groups. |
| **Safe multisig** | Lit's governance contracts above (DstackApp and AccountConfig) are administered by a Lit-controlled Safe multisig ([`0xF688411c0FFc300cAb33EB1dA651DBb3E6891098`](https://basescan.org/address/0xF688411c0FFc300cAb33EB1dA651DBb3E6891098)) on Base. The Phala KMS contract is governed separately by Phala (see above). Production deployments use a two-phase CI workflow: propose → approve via Safe UI → execute. |
