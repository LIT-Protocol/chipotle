When you call `api2.chipotle.litprotocol.com`, your request terminates inside an AMD SEV-SNP [Trusted Execution Environment](https://www.amd.com/en/developer/sev.html) (TEE) operated by [Phala Cloud](https://phala.com/). The processor signs an attestation report that says what the machine booted, and the code it's allowed to run is gated by smart contracts on Base — not by Lit Protocol or any Phala employee.

## Verify with the SDK

`verifyAttestation` from [`@lit-protocol/core-sdk`](https://www.npmjs.com/package/@lit-protocol/core-sdk) runs the whole check from your machine. It needs Node.js 22 or later.

```bash
mkdir lit-verify && cd lit-verify && npm init -y > /dev/null
npm install @lit-protocol/core-sdk

node --input-type=module -e "
import { verifyAttestation } from '@lit-protocol/core-sdk/attestation';
const p = await verifyAttestation('https://api2.chipotle.litprotocol.com');
console.log(p.platform, p.tcbStatus, p.tlsBinding, p.composeHash);
"
# sev-snp UpToDate verified 53dcf787de9b306be7299f35b16f0303da99f847eddff8d5037804bd2b951c3a
```

The compose hash changes with each release. The call throws an `AttestationError` if any check fails. When it returns, these hold:

| Result | What was checked |
|---|---|
| `platform: 'sev-snp'` | The report is signed by a genuine AMD processor, through AMD's certificate chain to a root key pinned in the SDK. Debugging is off. |
| A fresh report | The signed report commits to a random nonce the SDK generated for this call, so it cannot be a replay. |
| `osImageHash` | The signed launch measurement was recomputed from the firmware, kernel and boot parameters the machine declares, and that OS image is allowlisted in the Phala KMS contract on Base. |
| `appId`, `composeHash` | The signed `HOST_DATA` field binds Lit's app and the hash of the docker-compose document it runs, and that hash is allowlisted in Lit's DstackApp contract on Base. |
| `tlsBinding: 'verified'` | The TLS key of the connection the SDK used belongs to that same machine. Checked in Node.js. |

A client made with `createClient` runs this before its first request and pins every later connection to the verified TLS key, so the check protects the requests that carry your data. See [Production verification](/architecture/verification/index#production-verification).

## The Phala Trust Center report

Phala publishes an independent report for the production app. Viewing a report does not verify the connection your application uses to reach Lit; the SDK check above does.

The Trust Center URL contains our `app_id` (`3f91deaf16ff7c823ee65081d6bafa1ceea05ffc`). This same value is returned by `GET /info` on the live API and is the address of the on-chain [DstackApp contract](https://basescan.org/address/0x3F91Deaf16FF7C823eE65081d6bAFA1cEea05FfC) that governs which code the enclave is allowed to run.

## Inspect API metadata and on-chain policy

These commands inspect what the API reports and whether its reported compose hash is whitelisted on Base. They are preliminary diagnostics, not a substitute for cryptographic verification.

<Warning>
**These commands do not verify attestation or TLS termination.** An untrusted server can return an approved compose hash from `/info`. A `true` contract response confirms only that the supplied hash is allowed, not that this server is running it. Do not use these results alone to decide whether to send secrets.
</Warning>

```bash
# 1. What metadata does the API report? (Not authenticated attestation.)
curl -sf https://api2.chipotle.litprotocol.com/info \
  | python3 -m json.tool | head -20

# 2. Is the reported compose hash allowlisted on Base?
#    (Requires `cast` from Foundry — https://book.getfoundry.sh)
COMPOSE_HASH=0x$(curl -sf https://api2.chipotle.litprotocol.com/info \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["compose_hash"])')
cast call 0x3F91Deaf16FF7C823eE65081d6bAFA1cEea05FfC \
  "allowedComposeHashes(bytes32)(bool)" "$COMPOSE_HASH" \
  --rpc-url https://mainnet.base.org
# Expect: true
```

### What these commands leave out

The two commands above read claims from the server and a policy from the chain. They do not check a hardware signature, so they cannot tell an attested machine from one that copies its answers. The [SDK check](#verify-with-the-sdk) covers that, and the [Full Verification Guide](/architecture/verification/full-verification) shows how to repeat each of its checks by hand.

## On-chain governance you can audit

Smart contracts on Base together define what Lit Chipotle is allowed to do. Lit's own governance contracts are administered by a Lit-controlled Safe multisig — no single party can change them. The Phala KMS contract is a shared Phala-operated contract governed by a separate Phala-controlled Safe.
