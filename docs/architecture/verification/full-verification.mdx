title: "Full Verification Guide"
description: "Repeat each check the SDK makes on the live Lit API: hardware, application code, TLS and on-chain governance."
---

The Core SDK verifies the Lit API before it sends a request, and a client made with `createClient` does it without any setup. This guide walks through the same checks one layer at a time, so you can see what each one establishes and confirm the results yourself.

Some checks cannot reasonably be done by hand: verifying AMD's signature chain and recomputing the launch measurement need a program. Step 1 uses the SDK's verifier for those. It is one dependency-free file, [`lit-static/attestation.js`](https://github.com/LIT-Protocol/chipotle/blob/main/lit-static/attestation.js), that you can read. The later steps use ordinary tools to check the values it reports.

<Tip>
**New to TEE verification?** Read [What Is Attestation?](/architecture/verification/attestation) first, then work through the layers in order.
</Tip>

**Prerequisites:** Node.js 22 or later, `python3`, `openssl`, `curl`, and optionally [`cosign`](https://docs.sigstore.dev/cosign/system_config/installation/) and [`cast`](https://book.getfoundry.sh/getting-started/installation) (from Foundry).

## 1. Verify the attestation report (Platform)

**What this checks:** Is the server a genuine AMD SEV-SNP confidential VM, and what did it boot? The processor signs an attestation report with a key only that chip holds. The report carries a measurement of the launch state and a field, `HOST_DATA`, that binds the app the VM runs.

```bash
mkdir lit-verify && cd lit-verify && npm init -y > /dev/null
npm install @lit-protocol/core-sdk
```

```javascript verify.mjs
import { verifyAttestation } from '@lit-protocol/core-sdk/attestation';

const proof = await verifyAttestation('https://api2.chipotle.litprotocol.com');
console.log(JSON.stringify(proof, null, 2));
```

```bash
node verify.mjs > proof.json && cat proof.json
```

The call throws an `AttestationError` with a stable `code` if a check fails. A passing result looks like this, shortened:

```json
{
  "platform": "sev-snp",
  "appId": "3f91deaf16ff7c823ee65081d6bafa1ceea05ffc",
  "composeHash": "53dcf787de9b306be7299f35b16f0303da99f847eddff8d5037804bd2b951c3a",
  "osImageHash": "4771a29e03e93f0e2d5e37174cd8bb1112942c9689deb36b16c5df9e183d8623",
  "deviceId": "72791b7add93ac1f84c9d20ed738a3a091f90b92bf67914e48069086378ee9d5",
  "product": "Milan",
  "tcbStatus": "UpToDate",
  "tlsBinding": "verified",
  "tlsKeySha256": "76cd51ba00bcce67c5754e5615b686b366236ae09249d169b2374f5b87370de6"
}
```

`composeHash` changes with each release, and `tlsKeySha256` changes when a release replaces the VM. What the verifier did to produce it:

| Check | How |
|---|---|
| **Hardware** | Verified the report's signature with the chip's key (VCEK), and that key's certificate chain through AMD's intermediate (ASK) to an AMD root key (ARK) pinned in the verifier. |
| **Freshness** | Fetched `/attestation/v3?nonce=<random>` and required the signed report to commit to that nonce. |
| **Launch state** | Recomputed the launch measurement from the firmware, kernel, initrd and kernel command line the VM declares, and required it to equal the signed measurement. Refused a VM with debugging or migration enabled. |
| **Workload** | Required the signed `HOST_DATA` to equal the hash of the app identity document, which names the `appId` and `composeHash`. |
| **Governance** | Read the Base contracts and required both the compose hash and the OS image to be allowlisted. Step 4 repeats this. |
| **Channel** | Required the TLS key of its own connection to be bound to the same app. Step 3 repeats this. |

To look at the raw evidence, fetch it yourself. The nonce is any 32 random bytes in hex:

```bash
curl -sf "https://api2.chipotle.litprotocol.com/attestation/v3?nonce=$(openssl rand -hex 32)" \
  | python3 -c 'import json,sys; d=json.load(sys.stdin); print({k: (v if k in ("version","nonce") else type(v).__name__) for k,v in d.items()})'
# {'version': 3, 'nonce': '…', 'report_data': 'str', 'attestation': 'str', 'collateral': 'dict'}
```

`attestation` holds the signed report and the documents it binds. `collateral` holds the AMD certificates for the chip, so a verifier does not have to fetch them from AMD.

## 2. Verify the application code (Application)

**What this checks:** Is the TEE running the exact code you expect, with no modifications? This step verifies the Docker images and their configuration match what was built in CI from the public GitHub repository.

```bash
# Fetch app info (compose hash + full app-compose config)
curl -sf https://api2.chipotle.litprotocol.com/info > info.json

# 2a. Verify compose-hash: the SHA-256 of the app-compose.json config
#     (which includes docker-compose.yaml + metadata) must equal the hash the
#     attestation report binds, which Step 1 saved in proof.json.
python3 -c '
import json, hashlib
info = json.load(open("info.json"))
app_compose = info["tcb_info"]["app_compose"]
computed = hashlib.sha256(app_compose.encode()).hexdigest()
attested = json.load(open("proof.json"))["composeHash"]
print(f"Computed:  {computed}")
print(f"Attested:  {attested}")
assert computed == attested, "MISMATCH"
print("compose-hash OK")
'

# 2b. Verify all images use @sha256: digest pinning (no mutable tags)
python3 -c '
import json, re
info = json.load(open("info.json"))
compose_yaml = json.loads(info["tcb_info"]["app_compose"])["docker_compose_file"]
images = re.findall(r"image:\s*(.+)", compose_yaml)
assert images, "No image directives found"
for img in images:
    img = img.strip()
    pinned = "@sha256:" in img
    status = "OK" if pinned else "NOT PINNED"
    print(f"  {img[:80]}  {status}")
    assert pinned, f"Image is not digest-pinned: {img}"
print("All images digest-pinned OK")
'
```

**Verify image provenance with Sigstore** — Each image is signed with cosign (keyless, GitHub OIDC) during CI. This proves the image was built by GitHub Actions from the `LIT-Protocol/chipotle` repo:

```bash
# Install cosign: https://docs.sigstore.dev/cosign/system_config/installation/
# Verify each Lit-owned image digest extracted from the compose config above
cosign verify \
  --certificate-identity-regexp "https://github.com/LIT-Protocol/chipotle/.*" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
  <image>@<digest>
```

<Note>
The `dstack-ingress` image is a third-party dependency from the [dstack project](https://github.com/Dstack-TEE/dstack). It is Sigstore-signed from the dstack GitHub org, not from Lit's. To verify it, use `--certificate-identity-regexp "https://github.com/Dstack-TEE/dstack/.*"` with the same OIDC issuer. See the [dstack documentation](https://github.com/Dstack-TEE/dstack) for details on their signing and release process.
</Note>

## 3. Verify TLS terminates in the TEE (Network)

**What this checks:** Does your HTTPS connection end inside the attested VM, with no proxy in between that could read it?

Lit uses [dstack-ingress](https://github.com/Dstack-TEE/dstack-examples/tree/main/custom-domain/dstack-ingress) for TLS on its own domain. It runs inside the VM, generates the TLS private key there and obtains a Let's Encrypt certificate for it. It then publishes evidence at `/evidences/`:

| File | Contents |
|---|---|
| `cert-<domain>.pem` | The certificate it obtained. |
| `acme-account.json` | The Let's Encrypt account it used. |
| `sha256sum.txt` | The SHA-256 of each file above. |
| `attestation.json` | A SEV-SNP attestation whose signed report data is `SHA-256(sha256sum.txt)`. |

Because the report is signed by the processor and carries the hash of the manifest, the certificate in the manifest is one that this VM holds. Step 1 already verified that attestation and that it comes from the same app, and returned the hash of the attested TLS public key as `tlsKeySha256`. Check that the certificate you are served has that key:

```bash
# 3a. The key the verifier attested (from Step 1)
ATTESTED_KEY=$(python3 -c 'import json; print(json.load(open("proof.json"))["tlsKeySha256"])')

# 3b. The key of the certificate served to you now
LIVE_KEY=$(openssl s_client -connect api2.chipotle.litprotocol.com:443 \
  -servername api2.chipotle.litprotocol.com </dev/null 2>/dev/null \
  | openssl x509 -pubkey -noout \
  | openssl pkey -pubin -outform DER \
  | openssl dgst -sha256 -hex | awk '{print $NF}')

echo "Attested TLS key: $ATTESTED_KEY"
echo "Live TLS key:     $LIVE_KEY"
[ "$ATTESTED_KEY" = "$LIVE_KEY" ] && echo "TLS key matches — OK" || echo "MISMATCH"
```

During a release two VMs serve the hostname for a short time, each with its own key. If the keys differ, run Step 1 again and compare once more.

You can also check the evidence files against their manifest:

```bash
# 3c. Download the evidence files and check them against the manifest
mkdir -p evidences && cd evidences
curl -sf https://api2.chipotle.litprotocol.com/evidences/sha256sum.txt -o sha256sum.txt
CERT_FILE=$(curl -sf https://api2.chipotle.litprotocol.com/evidences/ \
  | grep -o 'href="cert-[^"]*\.pem"' | sed 's/href="//;s/"//')
curl -sf "https://api2.chipotle.litprotocol.com/evidences/$CERT_FILE" -o "$CERT_FILE"
curl -sf https://api2.chipotle.litprotocol.com/evidences/acme-account.json -o acme-account.json
shasum -a 256 -c sha256sum.txt
# acme-account.json: OK
# cert-api2.chipotle.litprotocol.com.pem: OK

# 3d. The certificate in the evidence has the attested key
openssl x509 -in "$CERT_FILE" -pubkey -noout \
  | openssl pkey -pubin -outform DER \
  | openssl dgst -sha256 -hex | awk '{print $NF}'
cd ..
```

<Warning>
**A matching checksum is not attestation by itself.** Anyone can serve a manifest and files that agree with each other. What makes the certificate trustworthy is the signed report in `attestation.json` that carries the manifest's hash, and the check that the report comes from the governed app. The verifier in Step 1 does both. Steps 3c and 3d only show you the files it worked from.
</Warning>

**Keeping the guarantee on later connections.** A check on one connection says nothing about the next one. A client made with `createClient` pins every API connection to the verified key. If you use your own HTTP client in Node.js, `createPinnedFetch` from `@lit-protocol/core-sdk/attestation` returns a `fetch` that refuses any other key:

```javascript
import { verifyAttestation, createPinnedFetch } from '@lit-protocol/core-sdk/attestation';

const proof = await verifyAttestation('https://api2.chipotle.litprotocol.com');
const pinnedFetch = await createPinnedFetch(proof.tlsKeySha256);
const res = await pinnedFetch('https://api2.chipotle.litprotocol.com/core/v1/version');
```

Browsers cannot inspect TLS certificates, so `tlsBinding` reports `'unsupported'` there and the other checks still run. Verify from a server when the channel matters.

## 4. Verify on-chain governance (Governance)

**What this checks:** Was the code running in the TEE authorized through on-chain governance? The compose-hash (a fingerprint of the entire application configuration) must be registered in a smart contract on Base before the CVM will accept it. This means deploying new code requires an on-chain transaction — you can audit the full history on Basescan.

The compose-hash must be registered in the **DstackApp** smart contract on Base before the key service will release keys to a CVM running it. A separate **Phala KMS** contract whitelists allowed OS images and KMS instances. You can inspect both on [Basescan](https://basescan.org).

**Finding the DstackApp contract address:** The DstackApp contract is the on-chain governance contract that authorizes what code the CVM can run. To find the correct address for a given CVM:

1. Go to the [Phala Cloud dashboard](https://cloud.phala.network) and look up the application by its `app_id` (available from `GET /info`). The dashboard shows the associated DstackApp contract address.
2. Verify the contract is the one your CVM is attached to by checking the `app_id` in the `/info` response matches the app registered in the contract on Basescan.

For Lit Chipotle production, the DstackApp contract is [`0x3F91Deaf16FF7C823eE65081d6bAFA1cEea05FfC`](https://basescan.org/address/0x3F91Deaf16FF7C823eE65081d6bAFA1cEea05FfC) (matches the `app_id` returned by `GET /info`). The Phala KMS contract is [`0x2f83172A49584C017F2B256F0FB2Dca14126Ba9C`](https://basescan.org/address/0x2f83172A49584C017F2B256F0FB2Dca14126Ba9C).

```bash
# Requires `cast` from Foundry (https://book.getfoundry.sh)

# Derive the DstackApp contract address from the CVM's app_id
DSTACK_APP=$(python3 -c 'import json; print("0x" + json.load(open("info.json"))["app_id"])')
echo "DstackApp: $DSTACK_APP"

# Check if the compose-hash is whitelisted in DstackApp
COMPOSE_HASH=$(python3 -c 'import json; print("0x" + json.load(open("info.json"))["compose_hash"])')
echo "Compose hash: $COMPOSE_HASH"
cast call "$DSTACK_APP" "allowedComposeHashes(bytes32)(bool)" "$COMPOSE_HASH" --rpc-url https://mainnet.base.org
# Expect: true

# Check if the OS image is allowlisted in the Phala KMS contract
OS_IMAGE=$(python3 -c 'import json; print("0x" + json.load(open("proof.json"))["osImageHash"])')
echo "OS image: $OS_IMAGE"
cast call 0x2f83172A49584C017F2B256F0FB2Dca14126Ba9C "allowedOsImages(bytes32)(bool)" "$OS_IMAGE" --rpc-url https://mainnet.base.org
# Expect: true
```

**Governance via Safe multisig:** Lit's on-chain governance actions are controlled by a Safe multisig ([`0xF688411c0FFc300cAb33EB1dA651DBb3E6891098`](https://basescan.org/address/0xF688411c0FFc300cAb33EB1dA651DBb3E6891098)) on Base. This Safe administers:

- **DstackApp** ([`0x3F91Deaf16FF7C823eE65081d6bAFA1cEea05FfC`](https://basescan.org/address/0x3F91Deaf16FF7C823eE65081d6bAFA1cEea05FfC)) — compose-hash whitelisting for the Lit Chipotle CVM
- **AccountConfig** — _details coming soon_

The **Phala KMS** contract ([`0x2f83172A49584C017F2B256F0FB2Dca14126Ba9C`](https://basescan.org/address/0x2f83172A49584C017F2B256F0FB2Dca14126Ba9C)) — which whitelists allowed OS images and KMS instances — is **not** administered by the Lit Safe. It is a shared Phala-operated contract whose `owner()` is a separate Phala-controlled Safe ([`0x3926658a072F82BAEa5e5a15e1Fed8a776F4a663`](https://basescan.org/address/0x3926658a072F82BAEa5e5a15e1Fed8a776F4a663), 2-of-3). Verify with `cast call 0x2f83172A49584C017F2B256F0FB2Dca14126Ba9C "owner()(address)" --rpc-url https://mainnet.base.org`.

Any Lit governance action (e.g., whitelisting a new compose-hash or upgrading the AccountConfig Diamond) requires Lit Safe signer approval. Production deployments use a two-phase workflow: CI proposes the transaction to the Safe, and signers approve it through the Safe UI before the deployment can proceed.
